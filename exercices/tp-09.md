# TP 9 — Analyse de performances complète sur un serveur cible

> Module : 6 — Performances et sécurité
> Durée estimée : 1h
> Difficulté : 3 / 5
> Type : Travaux pratiques guidés

## Mise en situation

Une application déployée sur la VM `srv-app` est jugée "lente" par les utilisateurs. Vous devez établir un diagnostic structuré : mesurer chaque couche (CPU, mémoire, disque, réseau), provoquer une charge contrôlée, identifier le goulot, et formuler une proposition.

## Objectifs

- Construire une baseline de performances avec les outils standards
- Provoquer des charges synthétiques pour CPU, disque et réseau
- Identifier la couche limitante et formuler une recommandation

## Prérequis techniques

### Logiciels à installer

- VM Linux (Debian 12 ou Ubuntu 22.04+) avec 4 vCPU, 4 Go RAM, accès sudo
- Paquets : `sysstat`, `procps`, `iotop`, `iftop`, `nethogs`, `stress-ng`, `fio`, `iperf3`, `htop`

### Vérification de l'environnement

```bash
sudo apt install -y sysstat procps iotop iftop nethogs stress-ng fio iperf3 htop
sudo systemctl enable --now sysstat
```

## Architecture cible

```
~/perf-lab/
  baseline/               (mesures à froid)
  load-cpu/               (sous charge CPU)
  load-disk/              (sous charge disque)
  load-net/               (sous charge réseau)
  rapport.md              (synthèse)
```

## Étapes

### Étape 1 — Préparer l'arborescence (5 min)

```bash
mkdir -p ~/perf-lab/{baseline,load-cpu,load-disk,load-net}
cd ~/perf-lab
```

Point de contrôle : structure créée.

### Étape 2 — Baseline (10 min)

Objectif : capter l'état au repos.

```bash
cd ~/perf-lab/baseline

uptime > uptime.txt
lscpu > lscpu.txt
free -h > free.txt
df -h > df.txt
ip -br link > links.txt
ss -s > ss.txt

vmstat 1 5 > vmstat.txt
iostat -xz 1 5 > iostat.txt
mpstat -P ALL 1 5 > mpstat.txt
sar -n DEV 1 5 > sar-net.txt
```

Point de contrôle : 9 fichiers créés et non vides, `%idle` du CPU > 90 %.

### Étape 3 — Charge CPU et profiling rapide (15 min)

Objectif : observer un système saturé en CPU.

1. Lancer la charge dans un terminal :
   ```bash
   stress-ng --cpu $(nproc) --cpu-method matrixprod --timeout 60s &
   ```

2. Pendant la charge, dans un autre terminal :
   ```bash
   cd ~/perf-lab/load-cpu
   uptime > uptime.txt
   mpstat -P ALL 1 10 > mpstat.txt
   pidstat -u 1 10 > pidstat.txt
   vmstat 1 10 > vmstat.txt
   top -b -n 1 | head -20 > top.txt
   ```

3. Après la fin :
   ```bash
   ps aux --sort=-pcpu | head -5
   ```

Point de contrôle : `mpstat` montre tous les cœurs proches de 100 % `%usr`, le `load average` dépasse `nproc`.

### Étape 4 — Charge disque (10 min)

Objectif : observer un I/O saturé.

1. Préparer un fichier de test :
   ```bash
   sudo fallocate -l 1G /tmp/fio-test 2>/dev/null || dd if=/dev/zero of=/tmp/fio-test bs=1M count=1024
   ```

2. Lancer un test fio en arrière-plan :
   ```bash
   fio --name=randrw --filename=/tmp/fio-test --size=1G --bs=4k \
       --rw=randrw --rwmixread=70 --ioengine=libaio --iodepth=32 \
       --runtime=60 --time_based --group_reporting \
       --output-format=json --output=fio.json &
   ```

3. Pendant le test :
   ```bash
   cd ~/perf-lab/load-disk
   iostat -xz 1 10 > iostat.txt
   sar -d 1 10 > sar-disk.txt
   sudo iotop -b -n 5 -o > iotop.txt
   ```

4. Une fois fio terminé :
   ```bash
   grep -E '"iops"|"bw_bytes"' ~/perf-lab/fio.json | head
   ```

   Sans `--output-format=json`, fio écrit son rapport texte habituel et
   ces deux clés sont absentes du fichier.

Point de contrôle : `iostat` montre `%util` > 80 % sur le device de `/tmp` pendant la charge.

### Étape 5 — Charge réseau (10 min)

Objectif : observer un réseau saturé.

1. Sur la VM, lancer iperf3 en serveur :
   ```bash
   iperf3 -s -D
   ```

2. Depuis le poste formateur (ou une seconde VM) :
   ```bash
   iperf3 -c <ip_vm> -P 4 -t 30
   ```

3. Pendant le test, sur la VM :
   ```bash
   cd ~/perf-lab/load-net
   sar -n DEV 1 10 > sar-net.txt
   ss -s > ss.txt
   ip -s link show | head -20 > ip-stats.txt
   sudo nethogs -t -c 5 > nethogs.txt 2>&1 || true
   ```

Point de contrôle : `sar -n DEV` montre du trafic significatif sur l'interface principale ; `ip -s link` ne montre pas d'`errors` ni de `dropped` croissants.

### Étape 6 — Identifier le goulot et rapport (10 min)

Objectif : produire `~/perf-lab/rapport.md`.

Squelette :

```markdown
# Rapport de performance — srv-app — <date>

## Baseline (système au repos)
- CPU idle : <chiffre>%
- Mémoire libre/dispo : <chiffres>
- I/O : devices, %util moyen
- Réseau : RX/TX moyens, erreurs

## Sous charge CPU
- %usr/sys/idle observés
- Load average pic
- Verdict : saturable / non

## Sous charge disque
- %util pic
- await pic
- IOPS et bande passante mesurés (extrait de fio.json)
- Verdict

## Sous charge réseau
- Débit pic (Mbps)
- Erreurs/dropped : oui/non
- Verdict

## Goulot identifié
- Couche limitante : CPU / mémoire / disque / réseau
- Justification chiffrée

## Recommandation
- Action prioritaire (au choix : tuner sysctl, scheduler I/O, ajout de RAM, scaling, etc.)
- Effort estimé
- Risque associé
```
