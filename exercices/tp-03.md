# TP 3 — Audit matériel et identification d'incidents

> Module : 2 — Modules de noyau, /proc, /sys et dépannage matériel
> Durée estimée : 45 minutes
> Difficulté : 2 / 5
> Type : Travaux pratiques guidés

## Mise en situation

Vous reprenez en astreinte un serveur Linux pour lequel l'équipe applicative signale des "comportements bizarres" : ralentissements ponctuels, redémarrages inattendus, message kernel cryptique vu un matin. La direction veut une fiche d'audit matériel exploitable et un avis : faut-il prévoir une intervention physique ?

## Objectifs

- Établir un inventaire matériel complet d'un serveur Linux
- Lire les compteurs SMART et les journaux noyau pour repérer un incident
- Produire une fiche d'audit lisible par un manager non technique

## Prérequis techniques

### Logiciels à installer

- VM Linux (Debian 12 ou Ubuntu 22.04+) avec accès sudo
- Paquets : `pciutils`, `usbutils`, `lshw`, `dmidecode`, `smartmontools`, `lm-sensors`, `util-linux`

### Vérification de l'environnement

```bash
sudo apt install -y pciutils usbutils lshw dmidecode smartmontools lm-sensors
which lspci lsusb lshw dmidecode smartctl sensors
```

## Architecture cible

```
~/audit-<hostname>/
  inventaire.md              (rapport final)
  raw/
    lscpu.txt
```

## Étapes

### Étape 1 — Préparer l'arborescence (5 min)

Objectif : isoler les sorties brutes.

```bash
mkdir -p ~/audit-$(hostname)/raw
cd ~/audit-$(hostname)
```

Point de contrôle : `pwd` retourne le bon répertoire et `ls raw/` est vide.

### Étape 2 — Inventaire matériel (15 min)

Objectif : capter le matériel exposé.

1. CPU :
   ```bash
   lscpu | tee raw/lscpu.txt
   cat /proc/cpuinfo | head -30 >> raw/lscpu.txt
   ```

2. Mémoire :
   ```bash
   lsmem | tee raw/lsmem.txt
   sudo dmidecode -t memory | tee raw/dmidecode-mem.txt
   free -h | tee -a raw/lsmem.txt
   ```

3. Stockage :
   ```bash
   lsblk -f -o NAME,FSTYPE,SIZE,MOUNTPOINT,LABEL,UUID | tee raw/lsblk.txt
   sudo smartctl --scan
   ```

4. Bus PCI et USB :
   ```bash
   sudo lspci -nnk | tee raw/lspci.txt
   sudo lsusb -t | tee raw/lsusb.txt
   ```

5. Vue synthétique :
   ```bash
   sudo lshw -short | tee raw/lshw-short.txt
   sudo dmidecode -t system -t bios | tee raw/dmidecode.txt
   ```

Point de contrôle : tous les fichiers `raw/*.txt` sont présents et non vides.

### Étape 3 — Santé disque et thermique (10 min)

Objectif : repérer un disque pré-tombant ou des températures hors-norme.

> **A lire avant de commencer.** Votre VM presente un disque **virtuel**
> (`vda`, virtio) et aucun capteur thermique : ni SMART ni `lm-sensors` n'ont
> de donnees physiques a lire. C'est normal et cela fait partie de
> l'apprentissage — savoir reconnaitre qu'un outil ne s'applique pas est aussi
> important que savoir le lancer. On execute donc les commandes pour observer
> le comportement reel en environnement virtualise, puis on interprete une
> sortie SMART **de machine physique** fournie par le formateur.

1. Constater le comportement de SMART sur un disque virtuel :
   ```bash
   DEV=$(lsblk -dn -o NAME,TYPE | awk '$2=="disk"{print $1; exit}')
   sudo smartctl -i /dev/$DEV | tee raw/smart-$DEV.txt
   sudo smartctl -H /dev/$DEV | tee -a raw/smart-$DEV.txt
   ```

   Sortie attendue en VM :
   ```
   /dev/vda: Unable to detect device type
   Please specify device type with the -d option.
   ```

   Noter dans le rapport : SMART inexploitable, **cause = disque para-virtualise
   sans passthrough**, ce n'est pas une panne. Sur un serveur physique la meme
   commande renvoie `SMART overall-health self-assessment test result: PASSED`.

2. Interpreter une sortie SMART de machine physique :

   Le fichier `ressources/module-02/smart-physique.txt` (sortie `smartctl -a`
   d'un disque SATA reel) est fourni avec le support :

   ```bash
   cp ressources/module-02/smart-physique.txt raw/
   grep -E "Reallocated_Sector_Ct|Current_Pending_Sector|Power_On_Hours|overall-health" \
       raw/smart-physique.txt
   ```

   Y relever et consigner :
   - `Reallocated_Sector_Ct` : secteurs realloues (une valeur qui **augmente**
     dans le temps annonce une fin de vie)
   - `Current_Pending_Sector` : secteurs en attente de reallocation
   - `Power_On_Hours` : anciennete du disque
   - le verdict global `PASSED` / `FAILED`

3. Capteurs (CPU/board) :
   ```bash
   ls /sys/class/hwmon/          # vide en VM : aucun capteur expose
   sudo sensors-detect --auto
   sensors | tee raw/sensors.txt
   ```

   Meme demarche : consigner l'absence de capteurs et sa cause (virtualisation),
   pas un dysfonctionnement.

Point de controle : le rapport distingue clairement **« outil non applicable en
environnement virtualise »** de **« materiel defaillant »**, et les quatre
indicateurs SMART ci-dessus sont releves depuis la sortie fournie.

### Étape 4 — Journaux noyau et incidents (10 min)

Objectif : extraire les erreurs significatives.

1. Erreurs critiques en cours de boot :
   ```bash
   journalctl -p err -k -b 0 | tee raw/dmesg-errors.txt
   ```

2. Recherche par mots-clés :
   ```bash
   for kw in "Hardware Error" "MCE" "I/O error" "thermal" "ata.*fail" "OOM"; do
     echo "=== $kw ==="
     dmesg -T | grep -iE "$kw" || echo "  (rien)"
   done | tee raw/dmesg-keywords.txt
   ```

3. Boot précédent (s'il y en a un) :
   ```bash
   journalctl --list-boots
   journalctl -p err -k -b -1 | tee raw/dmesg-errors-prev.txt 2>/dev/null || true
   ```

Point de contrôle : un avis se dessine déjà : présence ou absence de mots-clés "Hardware Error".

### Étape 5 — Rédiger la fiche d'audit (5 min)

Objectif : produire `inventaire.md` exploitable.

Créer `inventaire.md` avec ce squelette et le remplir à partir des sorties brutes :

```markdown
# Audit matériel — <hostname> — <date>

## Identité
- Modèle, serial, BIOS version
- OS et noyau
- Date d'audit, opérateur

## Composants
- CPU : modèle, cores, fréquence
- Mémoire : capacité, slots, modules
- Stockage : devices, taille, FS
- Réseau : interfaces, drivers
- Cartes additionnelles (PCI)

## Santé
- SMART (par device) : verdict + 3 indicateurs clés
- Températures : CPU max, board
- Capteurs anormaux : oui/non

## Incidents détectés
- Mots-clés trouvés dans dmesg avec extraits courts
- Hypothèse de cause

## Recommandation
- Aucune action / surveillance / intervention physique
- Échéance suggérée
```

Point de contrôle : le fichier tient sur une page écran et la recommandation est explicite.

## Livrable attendu

- Le répertoire `audit-<hostname>/` avec les sorties brutes
- Le rapport `inventaire.md` rédigé en français, lisible par un manager
- Une recommandation claire : aucune action / surveillance accrue / intervention physique sous X jours
